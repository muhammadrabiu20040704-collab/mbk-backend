MBK Network Connections

1. Overview

The Network Connections module enables students to establish mutual connections with other students in the MBK application.

The module supports sending, accepting, declining, and cancelling connection requests, viewing connection lists, and removing accepted connections.

2. Architecture

The module follows a layered architecture:

- Routes: Define HTTP endpoints and apply authentication middleware.
- Controller: Validates request parameters, obtains the authenticated user's ID, calls the service, and formats HTTP responses.
- Service: Implements connection business rules and coordinates database operations.
- Repository: Encapsulates MongoDB queries and updates.
- Model: Defines the MongoDB Connection schema and indexes.
- User Model: Stores each student's "connectionsCount".

Request flow:

"Client → Express Router → Authentication Middleware → Controller → Service → Repository/Models → MongoDB"

3. Connection Lifecycle

Pending

When Student A sends a connection request to Student B, a Connection document is created with the status "pending".

Accepted

When Student B accepts the request:

1. The connection status changes to "accepted".
2. Student A's "connectionsCount" increases by one.
3. Student B's "connectionsCount" increases by one.

These database changes are performed within a MongoDB transaction.

Declined

The recipient can decline an incoming pending request. The pending Connection document is deleted.

Cancelled

The requester can cancel an outgoing pending request. The pending Connection document is deleted.

Removed

Either participant can remove an accepted connection.

The accepted Connection document is deleted, and both students' "connectionsCount" values decrease by one.

4. Connection Data Model

The Connection document contains:

Field| Description
"requesterId"| ID of the student who sent the request
"recipientId"| ID of the student who received the request
"participantKey"| Unique key representing the pair of participants
"status"| "pending" or "accepted"
"createdAt"| Creation timestamp
"updatedAt"| Last update timestamp

Mongoose timestamps automatically maintain "createdAt" and "updatedAt".

5. Duplicate Prevention

The "participantKey" is generated by sorting both participant IDs and joining them with a colon.

This ensures that the same pair of students has the same key regardless of the order in which their IDs are supplied.

A unique database index prevents duplicate Connection documents for the same pair.

The service also rejects self-connection requests and handles duplicate-key errors.

If a pending request is declined or cancelled, its document is deleted, allowing a new request to be created later.

6. Authentication and Authorization

All connection routes require authentication.

The authenticated user's ID is obtained from the authentication context rather than trusting a user ID supplied in the request body.

Authorization rules include:

- Only the recipient can accept or decline an incoming request.
- Only the requester can cancel an outgoing request.
- Only participants can remove an accepted connection.
- Only accepted connections can be removed.

7. API Endpoints

The endpoints use the "/api/v1/connections" prefix.

Method| Endpoint| Description
"POST"| "/api/v1/connections/:userId/request"| Send a connection request
"GET"| "/api/v1/connections/requests/incoming"| Retrieve incoming requests
"GET"| "/api/v1/connections/requests/outgoing"| Retrieve outgoing requests
"GET"| "/api/v1/connections"| Retrieve accepted connections
"POST"| "/api/v1/connections/:connectionId/accept"| Accept a request
"POST"| "/api/v1/connections/:connectionId/decline"| Decline a request
"DELETE"| "/api/v1/connections/:connectionId/request"| Cancel an outgoing request
"DELETE"| "/api/v1/connections/:connectionId"| Remove an accepted connection

List endpoints support a "limit" query parameter. The default is 20, and the maximum is 50.

8. API Response Format

Successful responses use a consistent JSON structure:

{
  "success": true,
  "message": "Operation completed successfully.",
  "data": {}
}

The actual value of "data" depends on the endpoint.

9. Transactions and Data Consistency

Accepting a request updates the Connection document and both users' connection counts within a MongoDB transaction.

Removing a connection deletes the accepted Connection document and decrements both users' counts within a transaction.

These operations require a MongoDB deployment that supports transactions, such as a replica set or a compatible sharded cluster.
